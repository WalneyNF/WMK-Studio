WMK RAD Studio — Arquitetura da Central RAD

Como transformar bibliotecas, templates, regras e IA em um ambiente visual de desenvolvimento rápido.

Walney Moreira Klein — walneyk@hotmail.com

Central de manuais · Raio X do projeto · Design para programadores e IA

1. Objetivo

Permitir que o usuário escolha um template aprovado (Login V1/V2, Landing V1/V2, Cadastro V1/V2), configure o tema, informe entidades e ações e gere um documento visual editável dentro do WMK Studio. Posteriormente, o sistema poderá gerar código de aplicações mediante implementação própria, fora da responsabilidade exclusiva do editor de design.

Princípio: a IA propõe; um motor com regras valida e executa. Um template nunca será alterado definitivamente sem uma ação de edição ou versão explícita.

Não permitir componentes arbitrários como filhos de qualquer nó. Formulários são contêineres, campos ficam nas regiões de conteúdo, e botões de ação pertencem a barras de ações ou slots aprovados. Cada regra deve ser explícita e testável.

4. Manifesto de componente (proposta de contrato)

{
  "schemaVersion": "wmk-component-v1",
  "id": "wmk.button.primary",
  "version": "1.0.0",
  "name": "WMKButton",
  "category": "actions",
  "allowedParents": ["wmk.actionBar", "wmk.toolbar"],
  "props": {
    "label": {"type": "string", "required": true},
    "state": {"type": "enum", "values": ["normal", "disabled", "loading"]}
  },
  "styleTokens": {
    "background": "color.primary",
    "font": "font.body",
    "radius": "radius.medium"
  }
}

Esse manifesto é um contrato futuro da Central RAD, não um arquivo que a versão atual reconhece diretamente. Precisa ser mapeado para IDs concretos da biblioteca visual do WMK Studio.

5. Template parametrizável

{
  "schemaVersion": "wmk-template-v1",
  "id": "wmk.login.v2",
  "version": "2.0.0",
  "category": "auth/login",
  "theme": "wmk-dark",
  "rootComponent": "wmk.form.login",
  "slots": {
    "header": ["wmk.brand", "wmk.title"],
    "content": ["wmk.input.email", "wmk.input.password"],
    "actions": ["wmk.button.primary"]
  },
  "parameters": {
    "title": {"type": "string", "default": "Entrar"},
    "showRememberMe": {"type": "boolean", "default": false}
  }
}

Templates de login podem variar por estilo, disposição, responsividade ou fluxo, sem duplicar as definições-base de Input, Form e Button. Para alterar o padrão, crie uma nova versão com migração controlada para os projetos existentes.

6. Processo de geração com IA

  1. Usuário informa: “Crie um CRUD de clientes com o template Cadastro V2”.
  2. Central encontra a versão escolhida, tokens e componentes dependentes.
  3. IA devolve uma estrutura limitada, por exemplo entidade Cliente, campos Nome/E-mail/CNPJ, ações Salvar/Excluir.
  4. Validador checa IDs, hierarquia, slots, nomes, tipos, limites, dimensões e permissões.
  5. Motor converte JSON aprovado em comandos reais da engine/MCP; captura erros e pode desfazer.
  6. Abre um documento novo .wmk, sem sobrescrever o template original, e apresenta prévia editável.
  7. Usuário ajusta visualmente e pode optar por salvar como novo template versionado.
Separação fundamental: documentos visuais/protótipos não são aplicações com banco de dados. CRUD funcional, gráficos alimentados por dados, autenticação e deploy exigem etapa de geração e execução de software com testes e segurança.

8. Plano de execução por etapas

  1. RAD 0.1: estrutura de bibliotecas/JSON Schema, catálogo e testes sem IA.
  2. RAD 0.2: Theme Studio e Component Studio com seis componentes próprios, visualizados no editor.
  3. RAD 0.3: Template Studio: Login V1/V2, Cadastro V1, Landing V1; seleção e clonagem editável.
  4. RAD 0.4: validação de hierarquia/slots, versionamento e logs.
  5. RAD 0.5: compilar CLI, executar testes MCP, conectar Ollama local e gerar um login via plano JSON.
  6. RAD 0.6: Groq e outros provedores, mecanismos de timeout/429 e gestão protegida de credenciais.
  7. RAD 0.7: CRUD e dashboard de múltiplas telas, criação de novos templates pela IA com aprovação humana.
  8. RAD 1.0: estabilização, documentação ilustrada, testes automáticos e pacote público.

9. Regras essenciais de segurança e manutenção

  • A IA nunca executa código de shell, SQL ou comandos arbitrários do modelo.
  • Validação determinística de JSON, versão e componentes antes de modificar o documento.
  • Undo e rollback de ações compostas; logs com IDs de operação.
  • Credenciais remotas fora do projeto, em armazenamento protegido.
  • Arquivos do usuário não são enviados a serviços remotos sem autorização.
  • Bibliotecas oficiais são imutáveis por padrão; atualizações utilizam novas versões.
  • Sem execução de modelos externos dentro do sandbox WebAssembly de plugins; conectores precisam de serviço autorizado.
  • Templates possuem testes de criação, persistência, carregamento e invariantes de layout.
