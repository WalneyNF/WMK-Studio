1. Por que um programador precisa aprender essas propriedades?

Um editor visual transforma decisões sobre interface em objetos. Os conceitos são parecidos com sistemas de layout do HTML/CSS, controles de um formulário visual ou nós de interface de uma game engine, mas os desenhos não constituem automaticamente um programa com banco, autenticação e regras de negócio.

2. Exemplo — planejando uma tela de login

  1. Crie um Frame de 390 × 844 (dispositivo móvel) ou um de 900 × 600 (desktop).
  2. Aplique fundo #0B0217 ou superfície #1B0736.
  3. Adicione título de 32 px e subtítulo com uma descrição curta.
  4. Adicione rótulos e campos visuais de usuário e senha. Os campos ainda não armazenam ou validam dados.
  5. Adicione botão de ação principal, com fundo #8A2BE2 e texto claro.
  6. Distribua margens, espaçamentos e posições de forma consistente.
  7. Organize em camadas e componentes reutilizáveis.
  8. Se existir uma segunda tela, crie conexão de protótipo para simular a navegação.

Por que isso importa? A tela se torna uma especificação visual que você poderá reproduzir em HTML/CSS e integrar ao backend depois.

3. O que o projeto já oferece para IA

Na revisão do código do fork, foram encontrados:

  • docs/mcp.md — documenta servidor MCP com comandos para criar/editar camadas, inspecionar o documento e obter prévias, com modo headless e modo conectado ao editor.
  • docs/cli.md — descreve a ferramenta de linha de comando figcraft-cli, construída separadamente.
  • crates/mcp/ — implementação do servidor MCP no código.
  • crates/engine/src/content/templates.rs — registro de modelos iniciais editáveis e funções de construção de templates.

Estado atual: esses recursos são herdados do código original e constituem uma base de integração. Um painel nativo 'WMK AI Designer' com configuração pronta de Ollama/Groq ainda é uma proposta, não uma função instalada e testada neste fork.

O intermediário é indispensável: a IA não deve inventar identificadores de comandos nem escrever diretamente no formato binário nativo. Ela deve produzir um plano limitado a componentes e operações permitidas, e a engine deve construir o documento usando seus comandos reais.

5. Exemplo de contrato JSON proposto

Este exemplo é um desenho de arquitetura, e não um JSON que o programa atual já importa diretamente. Precisaremos implementar a conversão do contrato em comandos reais.

{
  "schemaVersion": "wmk-ui-v1",
  "intent": "login",
  "template": "wmk-login",
  "theme": "wmk-dark",
  "viewport": {"width": 390, "height": 844},
  "elements": [
    {"id": "titulo", "type": "text", "content": "Bem-vindo",
     "role": "heading"},
    {"id": "email", "type": "input", "label": "E-mail",
     "fieldType": "email"},
    {"id": "senha", "type": "input", "label": "Senha",
     "fieldType": "password"},
    {"id": "entrar", "type": "button", "label": "Entrar",
     "variant": "primary"}
  ]
}

O executor deverá validar IDs únicos, tipos permitidos, limites de tamanho, cores, coordenadas e quantidade de elementos. Também deverá usar placeholders explícitos para quaisquer imagens não fornecidas.

6. Integração com Ollama local

O Ollama disponibiliza APIs HTTP locais; a rota de conversa geralmente é POST http://127.0.0.1:11434/api/chat, com parâmetros como modelo, mensagens, format e stream. A documentação oficial descreve saídas estruturadas por JSON Schema no parâmetro format.

Para uma prova de conceito, podemos pedir ao modelo um JSON estruturado descrevendo elementos de um template de login, validar no backend e só então converter para operações do editor. É recomendado manter a porta local restrita ao loopback. Modelos pequenos podem gerar planos incompletos; devem receber templates curtos, validação e opção de correção.

Documentação oficial da API Ollama.

7. Integração com Groq e outros provedores

A API da Groq pode devolver JSON estruturado em modelos compatíveis, por meio de response_format. A disponibilidade de modos estritos varia por modelo. O plano gratuito depende dos limites vigentes da conta e não deve ser tratado como processamento ilimitado.

Recomendamos uma interface comum de provedores com nome, endpoint, identificador de modelo, temperatura, timeout, tentativas e suporte a saída estruturada. Chaves de API devem ficar em armazenamento protegido no backend/ambiente local, nunca dentro de documentos .wmk nem incorporadas ao frontend distribuído.

Documentação oficial Groq: Structured Outputs.

Uma etapa adicional, distinta, seria gerar código HTML/CSS/TypeScript a partir da especificação visual, seguido de testes e implementação de lógica de negócio. Isso não deve ser confundido com desenho automático de UI.

10. Segurança, desempenho e qualidade

  • Executar comandos somente de uma lista permitida; jamais executar código arbitrário emitido pelo modelo.
  • Exigir confirmação para sobrescrever projetos existentes; oferecer backup e desfazer.
  • Aplicar limites de elementos, tamanho de contexto e quantidade de chamadas.
  • Validar JSON mesmo quando o provedor oferecer saída estruturada.
  • Respeitar limites e erros de API, principalmente HTTP 429, timeouts e indisponibilidade do Ollama.
  • Não enviar arquivos privados a provedores remotos sem autorização clara.
  • Testar qualidade visual em tamanhos variados e marcar funcionalidades não verificadas.

11. Como estudar sem experiência em design

Em cada nova aula explicaremos: o que é a ferramenta, onde clicar, o que altera no resultado, quando usar, equivalência para programadores, erros comuns e exercício opcional. Você poderá ler em sequência; os exercícios permanecem como prática para os futuros usuários.

Sequência recomendada: Frame e coordenadas → tipografia → espaçamento e alinhamento → agrupamento → componentes → protótipos → templates → salvamento/exportação → automação MCP → IA.
