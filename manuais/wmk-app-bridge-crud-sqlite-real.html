WMK App Bridge 0.2: CRUD real com SQLite

React/TypeScript, backend Node.js, API HTTP e persistência no disco

Manuais · Relatório técnico anterior

1. Qual problema resolvemos?

A versão 0.1 já lia documentos .wmk e produzia React compilável, mas salvava os registros apenas no navegador. A versão 0.2 acrescenta backend Node.js e banco SQLite. O projeto gerado usa o manifesto de entidades e preserva a árvore do documento original. As ações do design ainda são configuradas em bindings JSON externos.

2. Arquitetura

arquivo.wmk + bindings.json
        |
WMK App Bridge: export.py
        |
React TS + Vite ---- /api ---- Node.js HTTP
                                |
                            SQLite real
                           data/wmk.sqlite

O banco é criado no primeiro uso. Campos e tipos vêm de dataModels no manifesto. O servidor usa SQLite nativo do Node.js e gera UUIDs para os registros.

3. Abrir e testar no Windows

cd D:\Ferramentas\figcraft\laboratorios\wmk-design-to-app\ridgeline-sqlite-v0.2
npm install
npm run dev:full

Abra o endereço do Vite no terminal, normalmente http://localhost:5173/. O servidor API abre em http://127.0.0.1:3337/. Teste http://127.0.0.1:3337/api/health. Preencha os campos no painel da direita, salve, edite, pesquise e exclua. Reinicie os serviços depois de salvar um item; ele deve continuar no banco SQLite.

5. Testes realmente executados

O backend passou na verificação de sintaxe Node.js. Uma suíte automatizada levantou a API local e verificou inclusão, listagem, consulta, alteração, rejeição de campos desconhecidos e ausência de campos obrigatórios. O processo foi desligado e reiniciado; o registro persistiu no SQLite. A exclusão removeu o item e a tentativa de excluí-lo de novo retornou HTTP 404. O frontend passou na checagem TypeScript e no build Vite com 33 módulos transformados. Um teste adicional iniciou os dois servidores e confirmou a página web servida pelo Vite e a resposta /api/health do SQLite através do proxy HTTP.

Não foi realizado teste visual automatizado do navegador; não afirmar fidelidade perfeita nem sucesso de todos os eventos visuais.

6. Limitações e decisões

O backend é local, sem autenticação, autorização ou migração de tabelas em produção. Não expor pela internet e não usar dados sensíveis. A conversão visual de vetores e Auto Layout ainda é aproximada. O WMK Studio desktop continua sem uma janela nativa Behavior Inspector; o contrato pode ser editado por JSON no estágio atual.

Próximos passos: implementar o Inspector no editor, ligar eventos diretamente aos componentes, usar SVG da engine, criar presets de formulário, acrescentar migrations e controle de usuários.
