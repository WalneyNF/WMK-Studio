2. Separação de responsabilidades

Navegador: React / TypeScript
  Formulário → botão Salvar → ClienteApi.criar()
      ↓ HTTP POST /api/clientes
Servidor: Node.js / Fastify
  Rota → autenticação e autorização → schema de validação
      ↓
  ClienteService (regras) → ClienteRepository (SQL)
      ↓
  Banco: SQLite, MariaDB ou PostgreSQL
      ↓
  Resposta HTTP → React atualiza a interface

No VFP, uma aplicação desktop pode chamar a camada de dados dentro do formulário; na Web, o frontend não deve conectar diretamente ao banco com credenciais. A separação API/backend é obrigatória em arquiteturas cliente-servidor comuns.

3. Comparando o evento Click

VFP

* cmdSalvar.Click()
THISFORM.Salvar()

React/TypeScript — botão

async function salvarCliente(nome: string) {
  const resposta = await fetch('/api/clientes', {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify({nome})
  });
  if (!resposta.ok) throw new Error('Falha ao salvar');
  return resposta.json();
}
// <button onClick={() => salvarCliente(nome)}>Salvar</button>

Node/Fastify — endpoint simplificado

app.post('/api/clientes', async (request, reply) => {
  // Validar request.body com schema na rota;
  // exigir autenticação e autorização em produção.
  const cliente = await clienteService.criar(request.body);
  return reply.code(201).send(cliente);
});

Os códigos são exemplos didáticos, sem contratos completos de segurança, persistência ou tipagem. Não são um CRUD funcional pronto.

5. Herança RAD versus código exportado

O usuário poderá configurar frmCadastro com eventos herdáveis (Novo, Salvar, Editar, Excluir) e derivar frmCadClientes. Internamente, o catálogo RAD terá um contrato de ações, por exemplo crud.save, vinculado a uma entidade. O exportador React poderá gerar composição, hooks, service de frontend e backend sem impor herança de componentes React, que geralmente é menos idiomática nesse ecossistema.

Ao exportar PHP, o mesmo contrato poderá ser transformado em controllers, services, models e views Laravel/CodeIgniter, usando as convenções reais de cada framework. Isso requer geradores distintos, testes e manutenção independentes.

7. Como converter isso em recursos WMK

  1. Criar biblioteca WMK de formulários e controles visuais.
  2. Definir catálogo de entidades: clientes, produtos, fornecedores, tipos e relacionamentos.
  3. Definir eventos de controles com identificadores semânticos (ex.: crud.save).
  4. Permitir sobrescrever ou estender rotinas herdadas por contrato versionado.
  5. Gerar primeiro uma stack funcional (React/TypeScript + Fastify + SQLite).
  6. Executar build, migrations, testes CRUD, validação e revisão visual.
  7. Adicionar adaptador PHP/Laravel ou CodeIgniter depois, sem alterar o catálogo visual.
  8. Acoplar Ollama/Groq apenas depois que o gerador determinístico funcionar.

8. Cuidados

Um formulário desenhado não define automaticamente autenticação, autorização, transações ou estrutura de banco. O gerador precisa de schemas e regras explícitas. Toda regra crítica deve ser validada no backend, e a aplicação exportada deve compilar e executar sem depender do editor WMK.

Esse fluxo é uma proposta para a evolução do fork. O WMK Studio atual possui editor visual e alguns geradores de trechos de código, mas ainda não é uma fábrica integrada de CRUDs full-stack.
